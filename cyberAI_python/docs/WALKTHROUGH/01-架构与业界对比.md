# 01 · 框架为什么这样分层 + 网上(大厂框架)怎么做

## 一、整体分层(为什么这么切)

```
frontend/ static html+js   ← 交付(看得见的界面)
web/  routers+deps+app.py  ← Web壳(FastAPI), 把能力变成 HTTP API
core/ llm+agent+tools      ← "发动机":LLM对话 + ReAct循环 + 工具管理
agents/ supervisor/base    ← 多Agent编排(一个能组团)
workflow/ knowledge/       ← 两个"能力引擎":DAG工作流 + 向量RAG
security/ database/        ← 底座:认证权限 + 数据存储
tools/  configs/*.yaml     ← 91个工具(纯数据声明, 不写代码)
```

**为什么这样切?** 核心思想一句话:**"能力与交付分离, 数据与代码分离"**
- LLM 厂商/模型 → 只影响 `core/llm.py`(换模型只改一处)
- 加一个工具 → 只在 `tools/configs/` 加一个 YAML(不用写代码)
- 加一个 HTTP 接口 → 只在 `web/routers/` 加一个函数
- 加一张表 → 只在 `database/models.py` 加一个类
每一层只依赖"下面一层", 不越级 → 后期好维护(你的核心要求)。

## 二、一次对话的完整链路(看懂就懂架构)

```
浏览器JS  --fetch POST /api/chat-->  web/routers/chat.py
   |                                     | auth_manager验token(RBAC)
   |                                     v get_or_create_agent() 返回 core.agent.Agent
   |        run_in_threadpool(agent.think)  ← 丢线程池, 不卡死别的请求
   |                                     | 进入 ReAct 循环:
   |                                     |  LLM(读 messages+tools) → 决策"调 dns_lookup"
   |                                     |  tool_registry 执行 dig → 结果回填 messages → 再问
   |                                     |  ...直到 LLM 不再调工具, 给出最终答案
   |                        v database.save_message(会话/消息入库)
   |<----- JSON {response, tool_calls} ----|
浏览器JS 渲染回复
```

对应的 **流式版**(/api/chat/stream) 同理,只是把上面 LLM/工具的过程用 SSE 逐事件发出去:
`tool_call → tool_result → llm(delta) → done`, 前端就能「看到它边想边调工具」。

## 三、网上主流框架怎么做(对比)

市面上没有"一步到位"框架, 主流是**自组装**:

| 框架 | 怎么做的 | 对比我们 |
|------|---------|---------|
| **LangChain / LangGraph** | 把 LLM调用/工具/记忆/检索做成可"链"对象; AgentExecutor 跑 ReAct 循环; LangGraph 用图状态机 | 我们=自研轻量版, 不引入大框架依赖, 代码可读可控 |
| **eino(Go)** | ByteDance 的 LLM app 框架, ADK 编排 agent + checkpoint + 上下文压缩都是现成的 | Go版用它; 我们手写等价逻辑(supervisor/checkpoint/context_budget)对齐 |
| **OpenAI Function Calling** | 模型原生支持"声明工具+返回要调的工具", 我们 `_handle_tool_calls` 用的就是它 | 我们直接用它, 不封装 |
| **框架帮你做什么** | 消息循环/工具解析/状态管理/厂商切换 | 这些我们已实现(core/agent + llm.py) |

**我们的取舍**: 不用 LangChain ——
1. **对齐 Go**: 要功能/行为跟 Go 版一致, 手写循环最直观(Go 也是 eino, 但我们对齐外部行为即可);
2. **可学习/可控**: 零依赖黑盒, 每一行都看得懂, 适合当你教学项目;
3. **轻量**: 91工具+单Agent+多Agent 而已, 引入 LangChain(几百MB+抽象层)反而冗。

## 四、一句话背框架

> **一个 Agent 大脑(ReAct循环) + 一个工具库(YAML声明) + 一层 Web壳(API) + 两个引擎(DAG工作流/向量RAG) + 底座(认证/数据)。**
> 框架自己动手, 不套现成大厂库, 为的是"看得懂、好维护、对齐 Go"。
